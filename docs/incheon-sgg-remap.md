## 2. 왜 `OLD_LAWDCD` 인가 — ★ 명칭 조인 금지

### 2-1. 명칭 조인은 실패한 방식이다

T018 의 `scripts/postgis/build_sido_remap.sql` 은 신·구 법정동명의 **꼬리 문자열을 조인**해 대응을
추론했다. 그 파일에는 이 문서를 가리키는 **deprecated 배너**가 붙어 있다(§12).

> **★ 60.70% 라는 수치를 정확히 읽을 것.** 그 스크립트 주석의
> *"양쪽이 모두 성립하는 402건 중 결론 일치는 244건(60.70%)"* 은 **명칭 조인의 정확도가 아니다** **[코드]**.
> 명칭 기반(가설b)과 *"시도 2자리만 치환"*(가설a)의 **결론이 서로 갈린 비율**이며, 원문은 이 값을
> **가설a 를 배제하는 근거**로 썼다. 둘 중 어느 쪽이 옳은지는 그 시점에 판정되지 않았다.
> 실제로 산출물 `lawd_sido_remap` 623행은 정본과 대조했을 때 **불일치 0** 이다 **[측정]**(§12).
> **그 판정을 원천이 대신해 준 것이 T026 의 `OLD_LAWDCD` 다.**

따라서 deprecated 사유는 **정확도 수치가 아니라 방법의 구조적 한계**다 **[판단]**.

### 2-2. 왜 명칭으로는 결정될 수 없는가

**① 동명은 전국 중복이다.** '중구'·'동구'·'서구'는 서울·부산·대구·대전에도 있다.
명칭으로 판정했다면 전국의 동명 구가 전부 오염됐을 것이다 **[코드]**(`remap_sigungu` docstring).

**② 인천 안에서도 결정되지 않는다.** 신 '금곡동'이 **2:2 로 중복**한다 **[측정]**(계획서 §1-4):

```
2812510600  제물포구 금곡동  ←  2814010600  (옛 동구 금곡동)
2829010700  검단구  금곡동  ←  2826011800  (옛 서구 금곡동)
```

같은 이름 '금곡동'이 서로 다른 구에서 서로 다른 옛 코드로 온다. **명칭만으로는 어느 쪽인지
알 수 없다.** 대응을 결정하는 것은 이름이 아니라 원천이 한 행에 함께 실어준 코드다.

**③ 접두만 갈아끼우는 것도 틀린다.** 신구 코드의 **뒤 5자리(읍면동 부분)가 같은 것은 9건뿐이고
70건은 바뀐다** **[측정]**. 즉 `28110xxxxx → 28125xxxxx` 식 접두 치환은 **88.6% 가 오답**이다.

### 2-3. 채택한 축

VWorld `법정동코드` dsId=**30505** 는 `OLD_LAWDCD` 컬럼을 직접 제공한다. **신 코드 행이 자기 옛
코드를 가리킨다.** 대응표 생성 SQL 은 이 컬럼으로 **코드 등가 자기조인**(`o.bcode = n.old_bcode`)
을 할 뿐, 명칭 컬럼을 조인 키로 쓰지 않는다 **[코드]**.

전국 범위 고아 스캔 결과 이 축의 결함은 **정확히 1건**이었다 **[측정]** — 그 1건이 §6 의 수동 보정이다.

## 3. ★ 왜 8자리(읍면동)가 최소 입도인가

**5자리 시군구 코드로는 분해가 불가능하다.**

```
옛 28260(서구)     → 서해구(28275) + 검단구(28290)      1:N
신 28125(제물포구) ← 28110(중구)   + 28140(동구)        N:1
```

시군구↔시군구는 **다대다**다. 서해구와 검단구는 **둘 다 옛 28260 하나**에서 나오므로 5자리만 보고는
어느 쪽인지 정할 수 없고, 제물포구는 **28110·28140 두 개에 걸친다**.

**1:1 로 확정되는 최상위 입도가 8자리 읍면동이다.** 그래서 대응표 `lawd_sgg_remap` 의 PK 는
`old_emd8`(8자리)이고, 응답 치환 함수도 8자리를 판정 키로 받는다 **[코드]**.

10자리(리 포함) 코드는 앞 8자리만 갈고 **뒤 2자리는 보존**한다. 전남·광주와 달리 리 재배정 예외표가
없는 이유는 **인천 옛 3구에 법정리가 존재하지 않기 때문**이다(전 지역 리코드 `00`) **[코드]**.

## 4. ★★★ 채택 방식: 안 A(응답 경계 치환) — 영구 불일치 경고 ★★★

> **DB 는 앞으로도 옛 코드다.** `28110`(중구)·`28140`(동구)·`28260`(서구).
> **응답에서만** `28125`(제물포구)·`28155`(영종구)·`28275`(서해구)·`28290`(검단구) 로 보인다.
>
> ### ★ WHERE 절·조인·필터에는 반드시 **옛 코드**를 써야 한다.
>
> ```sql
> -- ✗ 0건이 나온다. 버그가 아니다.
> SELECT * FROM address WHERE left(bcode,5) = '28125';
>
> -- ✓ 제물포구 데이터는 여기 있다.
> SELECT * FROM address WHERE left(bcode,5) IN ('28110','28140');
> ```
>
> API 응답에서 `28125` 를 보고 그 값을 그대로 SQL 에 넣으면 **조용히 0건**이다.
> 이 **DB↔API 영구 불일치는 버그가 아니라 설계다.** 안 B(DB 전면 remap)가 별도 태스크로 수행되기
> 전까지 유지된다.

안 A 를 택한 이유는 전남·광주(T018)와 같다 — 응답 정합성을 즉시 얻으면서 대규모 DB 이관의 비용·위험을
분리한다 **[판단]**. 다만 인천은 시도코드가 불변이라 **파티션 이동 비용 자체가 없으므로**, 후속
안 B 의 난이도는 전남·광주보다 낮다 **[판단]**.

## 5. 대응표 생성 절차 — 게이트 값은 **80**

```
scripts/load_lawd_code_v2.py                              CSV → lawd_code_v2 적재
  ↓
scripts/postgis/build_incheon_remap_from_old_lawdcd.sql   자동 79행   (OLD_LAWDCD 자기조인)
  ↓
scripts/postgis/lawd_sgg_remap_manual_fix.sql             원천 결손 1행 보정  (§6)
  ↓
scripts/postgis/lawd_sgg_remap_data.sql                   멱등 덤프(80쌍)
  ↓
                                                          = lawd_sgg_remap  80행
```

**최종 게이트 값은 80 이다.** 생성 SQL 의 게이트 `G-a` 는 자동 단계에서 **79** 를 기대하고
`"S4 후 80"` 이라고 명시한다 **[코드]**. 보정 SQL 의 게이트는 `G4-a`(전체 80) / `G4-b`(수동 1) /
`G4-c`(자동 79) 다 **[코드]**.

생성 SQL 은 **신 코드를 하드코딩하지 않는다.** 도출 규칙은 코드 산술뿐이다 **[코드]**:

```sql
WHERE left(n.bcode,2) = '28' AND left(n.old_bcode,2) = '28'   -- 인천 코드공간
  AND left(n.bcode,5) <> left(n.old_bcode,5)                  -- 시군구가 실제로 바뀐 행만
  AND right(btrim(n.bcode),2) = '00' AND right(btrim(n.old_bcode),2) = '00'   -- 읍면동 단위
  AND right(btrim(n.bcode),5) <> '00000'                      -- 시군구 자체 행 제외
  AND btrim(n.del_dt) = '';                                   -- 폐지되지 않은 행
```

구조 가드: 쌍 수가 `[70,90]` 범위 밖이거나, 다중 매핑이 1건이라도 있거나, 신 코드 접두가 `28` 이
아니면 `RAISE EXCEPTION` 으로 중단한다 **[코드]**.

두 표가 공존한다. **섞어 쓰면 안 된다** **[판단]**(계획서 §7-3 m-1):

## 6. 수동 보정 1행 — 유일한 인간 판단 상수

```
2811010100  중구 중앙동1가   →   2812510800  제물포구 중앙동1가
```

**신 코드 행이 VWorld 원본에 아예 없다**(원천 결손). 자동 79행이 80행이 되지 못한 유일한 이유다.

`scripts/postgis/lawd_sgg_remap_manual_fix.sql` 헤더에 기록된 근거 3종 **[코드]**:

1. **원천 부존재** — `lawd_code_v2` 에 `bcode='2812510800'` 행이 **없다**. 있는데 잘못된 게 아니라
   행 자체가 결손이다.
2. **DB exist 대조** — 옛 코드 `2811010100` 은 `exist=f`(폐지됨), 신 체계 쪽은 `exist=t`.
   즉 대응이 있어야 마땅한 자리다.
3. **코드 산술** — `28110101 + 7 = 28125108`. 인접 행들이 모두 `+7` 규칙을 따르며,
   이 값으로 채웠을 때 **`new_emd8` 충돌 0건**.

이 1행에는 `src='manual:vworld-30505-missing-row'` 가 붙는다. **자동 생성분(`src` 가 다름)과
구분 가능하며, 이것이 이 시스템의 유일한 인간 판단 상수다** **[코드]**.

롤백은 한 줄이다: `DELETE FROM lawd_sgg_remap WHERE src LIKE 'manual:%';`

결손 미보정 시 영향은 **130행** — parcel 50 · building 37 · address 43 **[측정]**.

## 8. fail-open 계약 — 표가 없으면 아무 일도 일어나지 않는다

`_load_sgg_remap` 은 표 부재·조회 실패 시 **전역을 비우고 `False` 를 반환한다** **[코드]**.
그러면 `remap_bcode` 의 `28` 분기와 `remap_sigungu` 가 **전부 항등함수**가 되어
**현행 응답이 그대로 유지된다(0건 회귀).**

세부 계약 **[코드]**:

- 대상 아님·표 미적재일 때 **원값 객체**를 반환한다. 문자열 `trim` 조차 하지 않는다
  (비대상 경로의 값 형태를 건드리지 않기 위함. 테스트 `U5` 가 `assertIs` 로 강제).
- 매핑표에 **없는** 대상 코드도 치환하지 않는다 — 없는 코드를 지어내지 않는다.
- `sigungu` 가 `None` 이면 만들어내지 않는다 — **없는 값을 채우는 것은 치환이 아니다.**

### ★ 부분 적재를 허용하지 않는 이유

**코드는 신 체계(`28125`)인데 구명은 여전히 '중구'인 상태는, 아무것도 안 한 것보다 나쁘다.**
사용자도 후속 대조 스크립트도 그 상태를 해석할 수 없다. 그래서 **코드 치환과 표기 치환을
스위치 하나에 묶었다.** 둘 다 되거나, 둘 다 안 되거나뿐이다.

## 9. 비-addr 행의 판정 키 — PIP 는 왜 금지 규칙에 저촉되지 않는가

### 9-1. 문제

인천 옛 3구의 `address` 행 중 **biz 68,869 · facility 1,403 은 `bcode` 보유 0건** 이다
(addr 은 70,115/70,115 전량 보유) **[측정]**. 즉 **자체 컬럼으로는 판정이 불가능하다.**

### 9-2. 해법

`area_pip` 이 좌표를 품는 **emd 폴리곤의 `code`** 를 함께 실어 보내 그 대역을 채운다 **[코드]**.

**이것은 명칭 조인이 아니라 좌표-폴리곤 공간 포함관계(ST_Contains)다.** 명칭 유사도로 대응을
추론하는 것이 아니라, 기하가 확정한 위치의 법정동코드를 읽는 것이므로 **금지 규칙에 저촉되지 않는다.**

인천 옛 3구의 `admin_boundary` emd 폴리곤 **80개가 `lawd_sgg_remap.old_emd8` 과 80/80 일치**한다
— 대응표와 **같은 코드축**이다 **[측정]**.

### 9-3. ★ 단, `b_code` 출력에는 PIP 값을 쓰지 않는다

```python
_bc_key = _bc or pip.get("bcode")        # 판정에는 PIP 폴백을 쓴다
...
"sigungu": remap_sigungu(_bc_key, sigungu),   # ← 판정 키: PIP 폴백 O
"b_code":  remap_bcode(_bc),                  # ← 출력:   자체 컬럼만. PIP 폴백 X
```

**PIP 값은 판정 전용이다.** 출력에 쓰면 전국 비-addr 응답의 `b_code` 가 **null → 값**으로 바뀌어
§9-4 회귀 가드(인천 외 시도 바이트 동일)를 깬다 **[코드]**.
비-addr 의 `b_code` 는 **종전대로 null** 이다.

## 10. 입력 좁힘 3단 — 검색 경로

응답만 바꾸면 사용자가 그 응답을 검색창에 다시 넣었을 때(round-trip) 0건이 된다. 그래서 입력 쪽에도
대응이 필요하다 **[코드]**:

| 단 | 조건 | 좁힘 대상 | 사전 |
|---|---|---|---|
| **1단** | 신 구명('제물포구'·'영종구'·'서해구'·'검단구') | **옛 8자리 집합** | `lawd_sgg_remap` |
| 2단 | 옛 구명('중구'·'동구'·'서구') 및 전국 시군구 | 5자리 | `lawd_sigungu`(254개) |
| 3단 | 시도명 | 2자리 폴백 | `SIDO_NM` |

### ★ 왜 1단이 필요한가

**`lawd_sigungu`(내비DB 추출 254개)에 신설 4구가 통째로 없다** **[코드]**. 그래서 신 구명 질의는
2단에서 `sgg_hit=∅` → 좁힘이 생략 → **3단 시도 폴백으로 흘러 '서해구 대곡동'이 검단구 대곡동을
반환한다**(과확장). 1단이 그 경로를 닫는다.

### ★ 옛 구명 입력은 계속 동작한다

'중구'·'서구' 같은 **옛 구명 입력은 2단에서 그대로 히트한다.** 1단은 신 구명만 잡으므로
기존 질의에 회귀가 없다. 표 미적재(`_HAS_SGG_REMAP=False`)거나 매칭 0이면 `emd8_hit` 이 비어
**2단이 현행과 100% 동일하게 동작한다**(fail-open) **[코드]**.

### 1단이 명칭 조인 금지에 저촉되지 않는 이유

| P1 이 금지한 것 | 1단이 하는 것 |
|---|---|
| 두 테이블의 명칭 컬럼끼리 **조인** | 사용자 입력 토큰 ↔ 라벨 컬럼 **등호 비교**(조인 0개) |
| 명칭 유사도로 대응을 **추론** | 이미 확정된 대응표에서 **코드를 꺼냄** |
| 모호성 발생(금곡동 2:2 등) | 없음 — `new_sgg_nm` 은 4개 값뿐, `old_emd8` 이 PK |

대응의 출처는 **원천이 한 행에 신구를 함께 준 `OLD_LAWDCD`** 이지 명칭 유사도가 아니다 **[코드]**.

## 11. 운영 트러블슈팅 — "왜 아직 중구가 나오나?"

### 11-1. 먼저 기동 로그를 볼 것

기동 시 **stderr** 로 나간다 **[코드]**. 실제 문자열은 다음 두 가지뿐이다:

```
geocode-api-pg: incheon sgg remap(T026): ON emd8=80
geocode-api-pg: incheon sgg remap(T026): OFF(중구/동구/서구 유지) emd8=0
```

바로 위 줄에 전남·광주 쪽 로그가 함께 나온다 — **둘은 독립이다**(§7):

```
geocode-api-pg: sido remap(안 A): ON emd=623 ri_exc=4 ri_emds=1411
```

**`OFF` 면 `lawd_sgg_remap` 테이블이 없는 것이다.** 코드 문제가 아니다.
fail-open 계약(§8)에 따라 응답은 현행(중구·동구·서구) 그대로 유지된 것이며, **정상 동작이다.**

`emd8=N` 의 N 이 **80 이 아니면 대응표가 불완전**하다. §5 의 생성 절차를 다시 확인할 것
(특히 수동 보정 1행이 빠지면 79 가 나온다).

### 11-2. 로그가 `ON emd8=80` 인데도 중구가 나온다면

| 증상 | 확인할 것 |
|---|---|
| 특정 응답 필드만 옛 이름 | §4-1 의 치환 지점 8곳 중 누락된 경로. 호출부가 `r` 에 `bcode` 를 싣지 않으면 `remap_sigungu` 가 fail-open 으로 원값을 돌려준다 |
| 비-addr(POI·building)만 옛 이름 | §9 의 `area_pip` 경로. `admin_boundary` 에 emd 폴리곤이 없으면 판정 키가 없다 |
| 신 구명으로 검색 시 엉뚱한 결과 | §10 1단. `lawd_sgg_remap` 미적재 시 3단 폴백으로 과확장된다 |
| 컨테이너가 옛 코드를 물고 있음 | 마운트 소스 확인. 이 프로젝트에는 워크트리가 여럿이고, 컨테이너가 **다른 워크트리를 bind mount** 하고 있는 사례가 실재한다. `docker inspect` + `md5` 대조를 먼저 하라 |

## 12. `lawd_sido_remap` 처분 — **유지한다. 이 태스크에서 제거를 실행하지 않는다.**

deprecated 인 것은 **표가 아니라 생성 방식(명칭 조인)** 이다. 그래서:

- ➡️ 재생성이 필요하면 **명칭 조인이 아니라 `OLD_LAWDCD` 축으로** 다시 만들 것
  (본보기: `scripts/postgis/build_incheon_remap_from_old_lawdcd.sql`)

### 12-1. `lawd_ri_remap_exception` — 사문화 상태이나 역시 제거하지 않는다

계획서 §1-8 은 이 표의 4행이 **사문화(dead letter)이며 내용도 틀렸다**고 기록한다 **[측정]**.

제거는 **로더 수정과 함께** 별도 태스크에서 해야 한다. **이 태스크에서는 실행하지 않았다.**
