# 역지오 도로명축 합성PNU 키조인 — 실측 근거

`/reverse` 의 도로명축을 KNN 최근접에서 **PIP 필지 내 합성PNU 키조인 우선 / KNN 폴백** 으로
바꾼 근거 수치다. (T029)

측정: 지적도 `ST_PointOnSurface` 로 독립 생성한 **2,401 좌표** — 3지역(종로/기장/완주) × 4지목
(대·도·임·전답) × 200 + 결정타 1. 변경 전후를 같은 스크립트로 호출해 대조했고, 변경 후는
**2회 독립 측정**해 아래 수치가 두 회차 완전 일치함을 확인했다.

> 595건 벤치마크(`scripts/595-corrections.csv`)는 질의 좌표 자체가 우리 순방향 출력이라
> 자기참조다. 역지오 정확도 근거로 쓰지 않는다.

## 1. 왜 raw 가 아니라 합성 PNU 인가

`address.bd_mgt_sn` 의 앞 10자리에는 **폐지된 법정동코드**가 박혀 있다. 그래서
`substr(bd_mgt_sn,1,19)` 로 그대로 조인하면 코드가 바뀐 지역에서 무너진다. 현재 코드가 든
`bcode` 를 앞에 붙여 만든 합성 PNU `bcode || substr(bd_mgt_sn,11,9)` 는 그 영향을 받지 않는다.

표본 2,401 PNU 를 `address`(`kind='addr'`)에 직접 대조한 결과:

| 지역 | raw | 합성 | 배율 | **대(垈)만** raw → 합성 |
|---|---|---|---|---|
| 종로 | 164/800 (20.5%) | 163/800 (20.4%) | ×0.99 | 123 → 122 |
| 기장 | 77/800 (9.6%) | 123/800 (15.4%) | ×1.60 | 61 → 98 |
| 완주 | **3/800 (0.4%)** | **121/800 (15.1%)** | **×40.3** | **2 → 101 (×50.5)** |
| 합계 | 244 | **407** | ×1.67 | |

완주 대지가 **1.0% → 50.5%** 로 종로 61.0% 에 근접한다. 법정동코드가 바뀌지 않은 종로에서는
두 방식이 거의 같고(합성이 1건 적다 — `bcode` 와 `bd_mgt_sn` 앞 10자리가 어긋난 개별 행으로
보이나 행 단위 규명은 하지 않았다), 코드가 바뀐 지역에서만 차이가 폭발한다. 원인 가설과
수치가 정확히 일치한다.

DB 기준 조인가능 **407 == 실제 응답 `address_source="pip_key"` 407**. 조인 가능한 곳에서
빠짐없이 조인됐다.

## 2. 왜 KNN 폴백이 부가기능이 아니라 정확성 요건인가

주소점(`kind='addr'`)은 건물에 부여되므로 도로·임야·전답 필지에는 대개 없다. 전국 필지의
**16.28%** 가 도(道)다. 폴백 없는 순수 키조인 전환은 도로 위 좌표에서 응답이 사라지는 회귀가
된다.

도(道) 표본 실측:

| 지역 | n | HTTP 200 | `knn` 경로 | `road` 빈 문자열 |
|---|---|---|---|---|
| 종로 도 | 200 | 200 | 195 | **0** |
| 기장 도 | 200 | 200 | 193 | **0** |
| 완주 도 | 200 | 200 | **200** | **0** |

침묵(빈 도로명) 0건. 그래서 **0행은 오류가 아니라 정상 경로**로 다루며, 거리 임계도 두지 않는다.

도 지목에서도 소수(종로 5·기장 7)가 `pip_key` 인데, 도로 필지 안에 주소점이 실제로 있는
경우다(예: 종로 수송동 146-8 → 구두수선대).

## 3. `WITH cand AS MATERIALIZED` 는 문법 장식이 아니다

빼면 PG12+ 가 CTE 를 인라인하고, 플래너가 `address_addr_geom_gix`(geom) 를 골라 합성키를
`Index Cond` 가 아닌 **`Filter` 로 강등**시킨다. 그 상태에서도 EXPLAIN 에는 인덱스명이 버젓이
나오므로 "인덱스명이 보인다" 만 확인하는 검증은 이 결함을 통과시킨다. 확인해야 할 것은 4가지다.

| # | 기준 | 조인 성공 | 0행 |
|---|---|---|---|
| 1 | `address_synth_pnu_idx` 등장 | ✅ | ✅ |
| 2 | 합성키가 **`Index Cond`** | ✅ | ✅ |
| 3 | `address_addr_geom_gix` **미등장** | ✅ | ✅ |
| 4 | 0행도 1~3 만족 + 같은 자릿수 | — | ✅ 0.152ms |

```
Index Scan using address_synth_pnu_idx on address a
  Index Cond: ((bcode || substr(bd_mgt_sn, 11, 9)) = '1111014800100010036'::text)
```

질의 시간 cold 85.9ms / **warm 0.143ms**, 0행 0.152ms(0행이 더 빠르다 = 전주행 없음).
생성 비용은 **34초 / 300 MB**(heap 5,722 MB 의 5.2%) — `kind='addr'` 부분 인덱스라
전체 1,628만 행이 아닌 1,069만 행만 담는다.
인덱스 실사용은 `pg_stat_user_indexes.idx_scan` **17 → 4,813**(2,401×2회)로 확인했다.

## 4. `ANALYZE` 로는 선택도 추정이 고쳐지지 않는다 — `CREATE STATISTICS` 가 필요하다

부분 인덱스를 만들고 `ANALYZE address` 를 돌려도 행 추정은 `rows=53029` 로 고정이었고
**플래닝에만 75.1ms** 가 들었다.

PostgreSQL `selfuncs.c` 의 `examine_variable()` 은 **부분 인덱스의 표현식 통계를 선택도 추정에
사용하지 않는다.** 표현식 인덱스가 자체 통계를 갖는 것은 맞지만 `WHERE kind='addr'` 이 붙는
순간 그 통계는 추정 경로에서 배제되고 `DEFAULT_EQ_SEL`(0.005)이 그대로 쓰인다.

해법은 PG14+ 의 독립 확장통계다 (`schema/11-address-search.sql` 에 동봉):

```sql
CREATE STATISTICS IF NOT EXISTS address_synth_pnu_stat
  ON kind, (bcode || substr(bd_mgt_sn, 11, 9)) FROM address;
```

플래닝 **75.1ms → 0.119ms**, 행 추정 **53029 → 1**(실측 평균 1.16행). 인덱스를 되돌릴 때는
`DROP STATISTICS` 도 함께 필요하다.

## 5. 응답이 실제로 어떻게 달라졌나

| 수치 | 값 |
|---|---|
| `parcel` 동일 + `road` 만 변경 | **48** |
| before 빈 `road` → after 채워짐 | 0 |
| before 값 → after 빈 문자열 (**회귀**) | **0** |
| `parcel` 이 바뀐 좌표 (지번축 회귀) | **0** |

**회귀 0건**이 이 표의 요점이다. 순증 0인 것은 표본이 필지 대표점이라 2,401건 전부 KNN 이
2.5km 안에서 주소점을 찾았기 때문이다(before 에 빈 `road` 가 애초에 없었다).

바뀐 48건이 개선인지는 축을 명시해야 말할 수 있다. 시군구 축으로는 before/after 가 전부 같아
**가릴 수 없다**. 그래서 응답 자신이 말하는 사실을 축으로 삼았다 — before 의 도로명은 정의상
KNN 최근접 주소점에서 오고, 그 최근접점의 필지는 `nearest[0].address.parcel` 에 찍혀 있다.

| 구분 | 건수 |
|---|---|
| before KNN 최근접점이 **남의 필지**였음 | **34** |
| before KNN 도 같은 필지 (같은 필지 안 다른 주소점) → **보류** | 1 |
| `nearest[0].address.parcel` 이 `null` 이라 판정 불가 → **보류** | 13 |

즉 **34건 증명 / 14건 보류**다. 그중 6건은 도로 이름 자체가 바뀌었다:

```
P 서울특별시 종로구 홍지동 69-39
B 서울특별시 종로구 홍지문길 51 (보현빌라)              ← 남의 필지
A 서울특별시 종로구 홍지문2길 20 (상명대학교 종합강의동)

P 서울특별시 종로구 신문로2가 170
B 서울특별시 종로구 송월길 18-7                         ← 남의 필지
A 서울특별시 종로구 새문안로 43-12 (I6)
```

또한 `pip_key` 407건 중 **62건**은 KNN 최근접점이 남의 필지였다(조인이 없었다면 섞일 수 있던
구간). 그중 34건은 도로명까지 달랐고 28건은 값이 같았다 — 집합건물 등 같은 도로명주소를 여러
필지가 공유하는 경우다.

> **PIP 가 항상 옳다는 주장은 하지 않는다.** 독립 교차검증에서 PIP 자체의 주소 복원율은
> 76.7% 다. 위 34건은 "after 가 더 좋은 주소" 라는 주장이 아니라 **"before 는 다른 필지의
> 도로명이었다"** 는 검증 가능한 사실이다. 두 주장은 다르며 후자만 근거가 있다.

## 6. 미해결 관측 — 부하 하에서의 소량 503

변경 후 측정에서 비200 응답이 **1회차 5건 / 2회차 4건**(2,401 중) 나왔다. 변경 전 측정에서는
**0건**이다.

- 실패 좌표가 회차마다 완전히 다르다 → 좌표 특성이 아니다
- 실패 좌표를 개별 재호출하면 **전건 200**(0.06~0.15초)
- 컨테이너 로그에 조인 실패 NOTE **0건** → 조인 질의가 예외를 낸 적은 없다
- postgres 로그의 원인 질의는 **KNN(`addr_at`) 쪽**이다:
  `could not attach to dynamic shared area` / `terminating background worker "parallel worker"
  due to administrator command` = `statement_timeout`(3s) 초과 취소

조인 질의가 늘린 DB 부하 때문에 기존 KNN 질의가 3초 벽에 닿는 빈도가 생겼다는 해석이 관측과
정합하지만, 부하 수준별 대조를 하지 않았으므로 **가설이지 증명이 아니다**. 8워커 동시 호출이라는
극한 조건에서만 나타나며 단건·순차 호출에서는 재현되지 않는다. 운영 전 재확인이 필요하다.

## 7. 재현

컨테이너 배선은 `docs/geocode-verify-container.md` 를 따른다. 검증 스크립트 호출 시
`OURS=http://127.0.0.1:8093` 을 **반드시** 앞에 붙인다 — 미지정 시 기본값이 운영 서버다.

좌표 집합은 한 번 만든 뒤 고정하고(before/after 가 같은 좌표여야 대조가 성립한다), 변경 전
측정을 **코드 수정 전에** 끝낸다.
