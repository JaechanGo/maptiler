## 0. 배경 — 왜 4단계인가

법정동코드 10자리 = **시도2 + 시군구3 + 읍면동3 + 리2**. 리 정보는

- `address.ri` (컬럼은 **이미 존재**하나 실서버 적재 여부 **[미확인]**),
- `address.bd_mgt_sn` 앞 10자리 (리 2자리 생존),
- `parcel.pnu` 9~10번째 2자리 (리 2자리 생존, `parcel.emd_cd` 는 8자리로 절단)

세 곳에 흩어져 있다. 사전 `lawd_ri(emd_cd, ri_cd, ri)` 는 **`address` 에서 파생**되므로,
`address.ri` 가 비어 있으면 사전을 만들 수 없고 기능도 동작하지 않는다.
그래서 **사전을 만들기 전에 그 사실을 1회의 HTTP 호출로 판정**하는 것이 게이트 G-1 이다.

| 단계 | 내용 | 사전 의존 | 이 단계에서 확인 가능한 완료 기준 |
|---|---|---|---|
| **P1a** | 코드 변경 ①(fail-open 플래그)·②(`addr_obj` ri 통과)·③(`parse` 리 토큰 분리)·④(`area_pip` emd) | 없음 | 3(`structure.ri` 부분)·5·6·8, (4 는 경계 적재 시) |
| **G-1** | `/reverse` 1회로 `address.ri` 채움 판정 | P1a 배포 | — (통과/중단 분기) |
| **P2** | `build_ri_dict.sql` 실행 → `lawd_ri` 구축 | G-1 통과 | 사전 자기검증 5종 |
| **P1b** | 코드 변경 ⑤(parcel 경로 `lawd_ri` 조인 + `pnu` NULL 안전 후필터) | P2 | 1·2·7·9 |

**P1a 가 무해한 이유** — 데이터가 없으면 아무것도 바뀌지 않도록 설계했다.
변경 ②는 `address.ri` 가 비면 `None`(현행과 동일), 변경 ③의 `ri` 키는 additive 이며 `dong` 값은 불변,
변경 ④는 `admin_boundary` 에 `emd` 레벨이 없으면 행 0(현행과 동일), 변경 ①은 조회 실패 시 `False` 로 리 로직 전체 비활성.
그래서 P1a 를 **게이트 판정 도구**로 쓸 수 있다.

### 게이트가 닫혔을 때의 중단 절차 (필수, 순서대로)

0. **산출물 4개를 모두 커밋한다.** 게이트가 닫혀도 코드·테스트·SQL·런북은 **후속 과제의 입력**이므로 폐기하지 않는다.
   커밋 메시지에 `G-1 미통과 — lawd_ri 미구축 상태로 동결` 을 명시한다.
1. P1a 는 무해하므로 **롤백하지 않는다**(그대로 둔다).
2. **P2 를 시도하지 않는다.** 시도하더라도 `build_ri_dict.sql` 의 하한 가드(`lo=15000`)가 `would_rows=0` 으로
   `RAISE EXCEPTION` 하며 거부한다 — **이중 안전망**이다.
3. **task-014 를 여기서 중단**하고 결과를 보고한다: **완료 기준 1·2·3 미해결.**
4. **"address 16.3M 재적재"를 별도 과제로 승격**한다. 본 과제 안에서 처리하지 않는다 —
   "재적재 0 · 백필 0" 이라는 계획의 전제 자체가 무너지므로 계획을 다시 써야 한다.
   (재적재 소요시간은 측정 기록이 없어 **[미확인]**, `TRUNCATE`+`INSERT` 라 중단 시 빈 테이블이 되므로
   **사전 스냅샷 확보 필수**, 폐쇄망 파일 전송 경로가 별도로 필요하다.)
5. **"계획대로 진행하되 미검증으로 남긴다"는 절충은 채택하지 않는다.** 게이트가 닫히면 코드가 옳아도 효과가 0 이다.

> **구 절차 `psql -f scripts/postgis/build_ri_dict.sql` 은 폐기됐다.** 실행하면

> `-v ON_ERROR_STOP=1` 을 빠뜨려도 막힌다 — 양쪽 다 로컬에서 실증했다 **[측정 2026-08-10]**.

**2단계다. 순서를 지킨다.**


| 가드 | 중단 조건 | 기대값 |
|---|---|---:|
| 선행 `lawd_code` | 없거나 행수 ≠ 53,387 → EXCEPTION | 53,387 |
| **재실행 방지** | `lawd_ri_old_20260810` 이 있으면 EXCEPTION | — |
| 총량 | 17,896 **± 50** 이탈 시 EXCEPTION | 17,896 |
| **폴백 시도** | 46 **외**가 섞이면 EXCEPTION (필터 누수) | 46 단일 |
| 폴백 행수 | 2,600 **미만**이면 EXCEPTION | 2,687 |
| 존재 티어 유일성 | 복수코드·복수이름 어느 쪽이든 > 0 이면 EXCEPTION | 0 / 0 |
| 원본 대조 고아 | 존재 티어가 원본에 없는 10자리를 만들면 EXCEPTION | 0 |
| 유가읍(27710259) | 리 수 ≠ 13 이면 EXCEPTION | 13 |

- **재실행 방지 가드의 의미** — 두 번째 실행은 백업 `lawd_ri_bak_20260810` 을 **신 사전으로 덮어써서**
  롤백 경로를 파괴한다. 그래서 교체 완료 표식(`lawd_ri_old_20260810`)이 있으면 진입 자체를 막는다.
  재구축이 정말 필요하면 §P-R 로 롤백을 **완료한 뒤** 실행한다.
- **폴백 시도 가드가 가장 중요하다.** 폐지 행 폴백은 전남(46)·광주(29)만 대상이다.
  다른 시도가 섞이면 폐지된 옛 코드가 현행 사전에 들어가 조용히 오염된다 — 즉시 중단.
  (로컬 실측은 46 단일 2,687행. 29 는 `lawd_dong` 교집합이 비어 0행이었다.)
- **중단해도 사전은 안전하다** — 구축·가드·교체가 한 트랜잭션이라 abort 되면 기존 사전이 그대로 남는다.

**왜 폐지 행을 섞는가** — 전남·광주는 법정동코드가 46/29 → 12 로 개편됐으나 우리 DB
(`parcel`·`building` 파티션키, `lawd_dong`)는 아직 46/29 체계다. 존재 행만으로 사전을 만들면
전남 리가 전부 12 로 바뀌어 **지금 동작하는 전남 리 지오코딩이 깨진다.** 폐지 행이 폴백을 만든다.
`lawd_dong` 에 실재하는 읍면동(46:421 / 29:201 = 622행)으로 한정하므로 무제한 유입은 아니다.

| **1** | `parcel` 축 정합률 (`pct`) | **`pct < 99` 면 P1b 로 진행하지 말고 중단** |
| 2 | 총 키 수 / 리 이름 종수 | 기록만. **구 실측 16,113 / 6,944** (2026-08-09) → **T018 신 사전 17,896** |
| 3 | `(emd_cd, ri_cd)` 복수 리이름 덤프 | 기록만. **구 실측 646행**. 3컬럼 PK 라 버려지는 리 이름 0 |
| 3b | `(emd_cd, ri)` 복수 리코드 | 기록만. **구 실측 534건**. 신 사전은 PK 가 `(emd_cd, ri)` 라 **구조적으로 0** — 후보를 1개만 반환한다 |
| 4 | `청평리` 존재 확인 | 행이 없으면 **완료 기준 1 달성 불가** — 기록 후 판단. 로컬 실측 `41820325\|21`, `51110380\|22` |

> **신 사전의 스키마 변경 주의** — PK 가 `(emd_cd, ri_cd, ri)` 3컬럼에서 **`(emd_cd, ri)`** 로 바뀌었고
> `exist boolean` 이 추가됐다. 컬럼명 `ri_cd` 는 유지된다(`geocode-api-pg.py:468` 이 이름으로 읽는다).
> PK 변경은 **fail-closed** 다 — 같은 읍면·같은 리 이름에 후보가 하나뿐이라, 틀리면 조회가
> 0건(무응답)이 되지 오답을 내지 않는다. 대신 **틀려도 눈에 덜 띄므로** 위 가드를 반드시 확인할 것.

- **자기검증 0(`lawd_dong` 축)이 특히 중요하다.** 실제 조회 경로(`geocode-api-pg.py` 의 지번 경로)는
  `lawd_dong` 으로 얻은 `emd_cd` 배열에 `lawd_ri.emd_cd` 를 맞춰 좁힌다. 이 값이 낮으면
  사전이 아무리 정확해도 조회가 0건이 되어 **기능이 무효**다. `parcel` 축(검증 1)만 보고 통과시키면 이 실패를 놓친다.
- 중단할 때는 **어긋난 키의 시도접두 분포**를 함께 보고한다(스크립트가 자동 출력한다):

  ```sql
  SELECT left(emd_cd,2) AS sido2, count(*)
    FROM lawd_ri r
   WHERE NOT EXISTS (SELECT 1 FROM parcel p
                      WHERE p.sido_cd = left(r.emd_cd,2)::char(2)
                        AND p.emd_cd  = r.emd_cd)
   GROUP BY 1 ORDER BY 2 DESC;
  ```
  현행 축(`bcode`)에서는 **0행이 정상**이다(로컬 실측 0행). 행이 나온다면 `address.bcode` 가
  구 코드 체계로 적재된 것이므로 사전이 아니라 **적재 데이터를 의심해야 한다.**

### 축 선정 이력 — 대체축 실측 완료·채택 (2026-08-09)

이 절은 과거에 「대체축 후보 (운영자 판단 사항)」이었다. **로컬 PostGIS 전량 실측으로 결론이 났고,
`build_ri_dict.sql` 은 이미 대체축으로 교체돼 있다.** 운영자가 다시 판단할 사항이 아니다.
아래는 왜 축이 바뀌었는지의 기록이며, 자기검증이 다시 99 미만으로 떨어졌을 때의 해석 근거다.

**폐기된 축** — `emd_cd = 시도2 리매핑(bd_mgt_sn 앞8)`, PK `(emd_cd, ri_cd)`

    키 16,419 · 자기검증 0 = 91.43% · 자기검증 1 = 91.43% · 충돌 27건 소실

`bd_mgt_sn`(건물관리번호) 앞 8자리는 **건물관리번호 발급 시점의 시군구 코드가 그대로 굳어 있다.**
청원군→청주시, 연기군→세종, 당진군→당진시, 이천군→이천시 등 **시군구 5자리** 개편은
**시도 2자리** 리매핑으로 구조적으로 교정할 수 없다. 어긋난 1,407키는 12개 시도에 고르게 퍼져 있어
(41:408 43:310 44:255 47:243 46:67 51:36 27:33 26:23 31:14 48:10 52:7 50:1)
리매핑 규칙을 더 추가해도 해소되지 않는다.

**채택된 축** — `emd_cd = left(btrim(bcode),8)`, `ri_cd = substr(btrim(bd_mgt_sn),9,2)`, PK 3컬럼

    키 16,113 · 자기검증 0 = 100.00% · 자기검증 1 = 100.00% · distinct_ri 6,944
    · (emd_cd, ri_cd) 복수이름 646건이나 3컬럼 PK 라 **소실 0**

`bcode` 는 도로명주소 본파일의 **현행** 법정동코드라 시군구 개편이 반영돼 있다. 단 끝 2자리는
전 행이 `'00'` 이라 리 코드를 담지 않으므로, 리 코드만 `bd_mgt_sn` 9-10 에서 취한다.

과거 이 축을 "이중축 UNION 은 신축 조합에서 충돌 646 → 폐기" 로 기록했었다. **그 646 건은 이 축에서도
그대로 나온다(자기검증 3 실측 646행). 폐기 사유였던 것은 충돌의 존재가 아니라 2컬럼 PK 가
충돌 시 리 이름을 하나만 남기고 버렸다는 점이다.** 조회 경로는 `WHERE ri = %s AND emd_cd = ANY(...)`
(변경 ⑤) 로 PK 를 타지 않으므로, PK 를 `(emd_cd, ri_cd, ri)` 3컬럼으로 넓히면 646 건이 모두
보존되어 **손실 0** 이 된다. 조회는 `lawd_ri_ri_emd_idx (ri, emd_cd)` 가 따로 받는다.

**남는 한계 (fail-soft, 무회귀)** — ~~이 사전은 address(도로명주소 건물 DB)에서 유도되므로
**건물이 없는 리는 수록되지 않는다.** 법정리 약 19,000 대비 16,113 → 약 3,000 개 미수록.~~
**→ T018 에서 해소됐다.** 마지막 문장이 예고한 "행안부 법정동코드 전량 파일 적재"를 실제로 수행해
사전이 17,896행이 됐고, 미수록 리 문제와 `setdefault` 오염이 함께 사라졌다. 위 §P2 참조.

원문 기록: 실측 예로 전북 완주군 소양면 월상리는 address 에 아예 없어(충북 월상리 207행만 존재)
리 좁힘이 걸리지 않았다. 미수록 리는 필터가 적용되지 않을 뿐 종전과 동일하게 동작하는 fail-soft 였다.

### 자기검증 중단 시 정리

> **T018 이후**: 신 스크립트는 가드·구축·교체가 **한 트랜잭션**이라 아래 서술의 전제
> (「자기검증은 COMMIT 이후라 보호되지 않는다」)가 성립하지 않는다. 어느 가드에서 걸리든
> 기존 사전이 그대로 남는다. 다만 **두 번째 실행은 재실행 방지 가드가 막으므로**, 재구축하려면
> §P-R 로 롤백을 먼저 완료해야 한다. 아래는 구 스크립트 기준 서술이다.

자기검증 0·1 은 `COMMIT` **이후**에 실행되므로, 이 시점에 `lawd_ri` 는 이미 커밋돼 있다.
(would_rows 가드 실패는 트랜잭션 롤백으로 보호되지만, 자기검증 실패는 그렇지 않다.)
`pct < 99` 로 중단했다면 **P1b 를 배포하지 말고**, 원인을 규명한 뒤 스크립트를 재실행한다
(재실행이 `DROP`→`CREATE` 로 멱등하게 갈아끼우므로 수동 `DROP TABLE lawd_ri;` 는 불필요하다).
사전을 완전히 걷어내려면 §P-R 참조.

### 재정의 기준 2 의 달성 가능성 확인 (P2 이후 1회)

```sql
SELECT p.emd_cd, count(*) FROM parcel p
JOIN lawd_ri r ON r.emd_cd = p.emd_cd
WHERE r.ri = '청평리' AND p.ji_main = 432 AND p.ji_sub = 11
GROUP BY p.emd_cd;
```

- **2행 이상** → **재정의된 기준도 달성 불가.** 기준을 `q=청평면 청평리 432-11` 로 다시 정의해야 한다.

**로컬 실측 (2026-08-09): `41820325 | 1` — 1행. 재정의 기준 2 통과.**
API 실측도 일치했다: `q=청평면 청평리 432-11` → parcel 1건, `structure.ri="청평리"`,
`b_code="4182032500"`. `display.full` 에는 리가 나오지 않는다(도로명주소 표기 규칙상 정상).

### 완료 기준 1 의 재정의 (필수)

원래 기준 `q=가평군 청평면 청평리 432` 은 **전제가 틀렸다.** 리 좁힘이 정상 동작하면 이 질의는 **0건**이며
그것이 정답이다. `ji_main=432, ji_sub=0` 인 필지의 리 코드는 22~27 뿐이고 **21(청평리)은 존재하지 않는다.**
기존의 6건은 서로 다른 6개 리의 432번지를 섞어 보여 준 **오답**이었다.

- **기준 1 을 `q=청평면 청평리 432-11` → parcel 1건 · `structure.ri="청평리"` 로 재정의한다.**
- 리 좁힘이 실효함을 보이는 대조 실측(로컬):
  `강원 춘천 신북읍 천전리 300` → **1건 `ri='천전리'`** / `신북읍 300` → 3건 `ri=null`
- **부수 문제(별건)**: 필지 0건일 때 POI 폴백이 그 자리를 무관한 localdata 10건(안경원·편의점 등)으로
  채운다. 리 파이프라인과 무관한 게이팅 문제이므로 여기서 고치지 않는다.

### P-R-2. 사전 롤백 (T018 신 사전 → 구 사전)

**신 스크립트는 멱등이 아니다.** `build_ri_dict_from_lawd_code.sql` 은 교체 시 구 사전을
`lawd_ri_old_20260810` 으로 옮겨 두고, 그 존재를 재실행 방지 표식으로도 쓴다. 두 번째 실행을
가드가 막는 이유는 백업 `lawd_ri_bak_20260810` 이 **신 사전으로 덮어써지는 것**을 막기 위해서다.

구 사전으로 되돌리려면 — 두 테이블 이름을 맞바꾼다(인덱스 이름 충돌을 먼저 푼다):

```sql
BEGIN;
  -- 인덱스 이름을 먼저 비운다. ALTER TABLE RENAME 은 인덱스 이름을 바꾸지 않으므로
  -- 이 단계를 건너뛰면 두 번째 RENAME 에서 'relation already exists' 가 난다.
  ALTER INDEX lawd_ri_pkey                   RENAME TO lawd_ri_t018_pkey;
  ALTER INDEX lawd_ri_ri_emd_idx             RENAME TO lawd_ri_t018_ri_emd_idx;
  ALTER INDEX lawd_ri_emd_cd_idx             RENAME TO lawd_ri_t018_emd_cd_idx;

  ALTER TABLE lawd_ri                RENAME TO lawd_ri_t018;
  ALTER TABLE lawd_ri_old_20260810   RENAME TO lawd_ri;

  ALTER INDEX lawd_ri_old_20260810_pkey       RENAME TO lawd_ri_pkey;
  ALTER INDEX lawd_ri_old_20260810_ri_emd_idx RENAME TO lawd_ri_ri_emd_idx;
COMMIT;

-- 확인: 16,113 이어야 한다(구 사전).
SELECT count(*) FROM lawd_ri;
```

- 롤백 후에는 재실행 방지 표식(`lawd_ri_old_20260810`)이 사라지므로 신 스크립트를 다시 돌릴 수 있다.
- `lawd_ri_bak_20260810`(구 사전 복제본, 16,113행)은 **인덱스 없는 안전망**이다. 위 교체가 꼬였을 때
  `CREATE TABLE lawd_ri AS SELECT * FROM lawd_ri_bak_20260810;` 로 복구한 뒤 PK·인덱스를 다시 만든다.
- **구 사전은 `exist` 컬럼이 없고 PK 가 3컬럼**이다. 롤백하면 `geocode-api-pg.py` 의 리 조회가

- `address.bcode` 리 자리 백필까지 되돌리려면 사전 롤백만으로 부족하다 —
  `docs/ri-backfill-production-runbook.md` 의 롤백 절을 따른다.

## 부록 B. 이번 범위에서 해결되지 않는 것

### ★ DB(46/29) ↔ API 응답(12) 영구 불일치 — T018 Phase 3 안 A (2026-08-10)

> **읽지 않고 이 DB 를 만지면 반드시 사고가 난다.** 같은 고지가 세 곳에 있다:
> `server/geocode-api-pg.py` 의 `T018 안 A` 블록 주석 · `lawd_ri.exist` 의 `COMMENT ON COLUMN` ·
> 그리고 여기. 세 곳이 어긋나면 코드 주석이 정본이다.

전남광주통합특별시(시도코드 `12`) 출범으로 `46`(전라남도)·`29`(광주광역시)는 법정동코드 원본에서
**폐지**됐다. 그러나 이 서버의 `address`·`parcel`·`building`·`admin_boundary` 는 여전히 46/29 로 적재돼
있고, `parcel`·`building` 은 `sido_cd` 파티션 키까지 46/29 다(코드를 바꾸면 8.1M 행 row movement).

**안 A 는 DB 를 그대로 두고 API 응답 경계에서만 12 로 치환한다.** 결과:

| | 값 체계 |
|---|---|
| DB 컬럼 (`address.bcode`, `parcel.pnu`, `admin_boundary.code`, `lawd_ri`) | **46 / 29** |
| geocode API 응답 (`address.b_code`, `areas[].code`, `structure.sido`) | **12 / 전남광주통합특별시** |

이 상태에서 **하면 안 되는 일**:

1. **응답의 `b_code` 로 DB 를 조회** — `WHERE bcode LIKE '12%'` 는 항상 0건이다.
2. **SQL `WHERE`·`JOIN`·필터에 `12` 를 넣는 것** — 치환은 응답을 만드는 순간에만 일어난다.
   (`geocode-api-pg.py` 의 `remap_bcode()`/`remap_sido_name()` 은 응답 조립부에서만 호출된다.)
3. **`lawd_ri` 에서 `exist=false` 행을 지우는 것** — 46/29 폐지 리 코드 폴백이며 안 A 가 유지되는 한 필수다.
4. **`lawd_sido_remap` 을 지우거나 비우는 것** — 비면 `_load_sido_remap()` 이 fail-open 으로 꺼지고
   응답이 조용히 46/29 로 되돌아간다(기동 로그 `sido remap(안 A): OFF(46/29 유지)` 로 확인).

**검색 입력은 양방향으로 성립한다** — 응답으로 받은 `전남광주통합특별시`(또는 `전남광주`)를 그대로
검색창에 다시 넣어도 내부에서 `전라남도`·`광주광역시`로 역치환되어 조회된다(§B-3). 다만 이는
**geocode API 를 통할 때만**이고, DB 를 직접 치는 도구·배치·대조 스크립트에는 적용되지 않는다.

**후속 대조 스크립트 주의** — 행안부/VWorld 문자열 대조기는 이제 전남·광주 건에서 우리 응답의 시도
토큰이 `전남광주통합특별시`로 나온다. 기준값과 비교하기 전에 시도 토큰을 정규화해야 하며, 그러지
않으면 전남·광주 전건이 불일치로 잡힌다.

**안 A 는 최종 상태가 아니다.** 안 B(`parcel`/`building` 파티션 포함 전면 remap)가 채택되면 DB 가 12 로
이관되고 `lawd_sido_remap`·`lawd_ri_remap_exception`·`lawd_ri.exist`·`remap_*()` 는 전부 불필요해진다.
안 B 인계 자료: `docs/jeonnam-gwangju-planB-handover.md`.

### 그 밖에 해결되지 않는 것

- **응답 안에서 `b_code`(12) 와 `h_code`(46/29) 가 어긋나는 것** — 안 A 는 **법정동코드만** 치환한다.
  구 주석은 `h_code` 를 "통계청 행정동코드라 대상 아님"이라 했으나 **거짓이었다**. **[측정 2026-08-10,
  `address` TABLESAMPLE SYSTEM(1)]** `hcode` 앞 2자리는 `bcode` 앞 2자리와 **100% 일치**한다
  (46→46 12,626 / 29→29 1,195 / 36→36 656 / 47→47 13,653, 교차항 0건). 즉 `address.hcode` 는
  **행안부 행정동코드**로 시도 2자리 공간을 법정동코드와 공유하므로, 원리상 치환 대상이 될 수 있다.
  그럼에도 치환하지 않는 이유는 **대응표가 없기 때문**이다 — 원본 `lawd_code` 는 법정동코드뿐이고,
  행정동은 시군구·읍면동 재편이 법정동과 다르게 잡힐 수 있어 **앞 2자리만 갈아끼우는 방식은 금지**다
  (명칭 기반 검증에서 402건 중 244건 = 60.70%만 일치 → 약 39% 오답). 해소는 안 B 몫이며, 그때
  **행안부 행정동코드 대응표를 별도로 확보**해야 한다. 그때까지 `h_code` 를 12 체계로 가정하지 말 것.
- **`areas[]` 가 두 코드체계를 섞어 반환하는 것** — 안 A 적용 후에도 `type='emd'` 항목은 12 체계로,
  `type='adm_dong'` 항목은 통계청 행정동코드(여기서 `29`는 **광주가 아니라 세종**)로 나온다.
  `adm_dong` 을 치환하면 세종 응답이 파괴되므로 의도적으로 남긴 상태다. 안 B 에서도 `adm_dong` 은
  별개 체계라 그대로 남는다.
- **`areas` 의 리 레벨 항목** — `admin_boundary` 에 리 경계가 적재돼 있지 않다. 경계 소스 확보가 별도 과제다.
  (`reverse()` 는 `level` 필터 없이 `ST_Contains` 만 하므로, 행이 들어가면 코드 변경 없이 나온다.)
- **POI structure 의 `sido`/`sigungu`** — 해당 레벨 경계 소스가 서버에 없다. `emd` 만 변경 ④로 채워진다.
- **산번지 혼입** — `san` 은 현행 `null` 유지.
- **세종·군위의 5자리 코드 재편** — 2자리 시도 리매핑으로는 처리 불가. 별도 과제.
- **`q=청평리 432-11` 을 필지로 만드는 것** — 읍면동 토큰이 없는 질의는 게이팅에 의해 사전을 타지 않는다.
  게이팅을 풀면 상호명 오탐 20,078건이 되살아난다. **트레이드오프는 운영자 판단 사항이다.**
